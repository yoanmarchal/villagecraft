# App: state, sharing, interaction, UI

Grid controller and undo, persistence and share links, scene interaction, loading screen, toolbar and control panel.

- **Grid mutations go through the controller**: after mutating the `VillageGrid` (add/remove/clear/generate), call `useGridControllerStore.getState().commit()` — it records an undo snapshot (`History` in [src/history.ts](../src/history.ts), states = `{ blocks: exportBlocks(), terrain: grid.terrain }`) and triggers the scene refresh. Don't call the refresh callback directly. Undo/redo restore via `grid.replaceBlocks()`, which keeps unchanged cells from replaying their spawn animation. Resizing the grid (new `VillageGrid`) resets the history.
- **Share links**: [src/store/shareLink.ts](../src/store/shareLink.ts) encodes `{ gridSize, blocks, terrain }` as `#v=<base64url>` (1 byte per value, format version first — bump it if the layout changes; v2 added the terrain seed and sculpt, v1 links are still read). `consumeSharedVillageLink()` runs in `main.tsx` before the first render. Grid bounds live in [src/config/gridConfig.ts](../src/config/gridConfig.ts).
- **Changing a persisted default**: `persist` stores the whole control state, so a new default never reaches existing users on its own. Bump the store `version` and extend `migrateControlState()` in [src/store/controlStore.ts](../src/store/controlStore.ts): replace a key only if it still equals the old default, delete removed keys (tested in `controlStore.test.ts`).
- **Scene/interaction**: [src/components/VoxelScene.tsx](../src/components/VoxelScene.tsx) (R3F canvas, OrbitControls, click-to-add/remove), reading scene/lighting/postFX values from [src/store/controlStore.ts](../src/store/controlStore.ts). Only a large invisible plane (below the lowest terrain) has pointer handlers; its event's `ray` is then walked through the voxel grid by `raycastVoxels()` ([src/utils/voxelRaycast.ts](../src/utils/voxelRaycast.ts): 2D DDA over columns, each with its own level `baseOf(x, z)`, the bottom cell extending down as the plinth) and intersected with the terrain by `raycastGround()` — the nearer of the two wins — so the click targets the first block under the cursor, not the ground behind it, and never uses `event.point` — never raycast the merged meshes (~1 M vertices, no BVH). `targetColumn()`: demolish / build on a top face → that column; build on a side face → the neighbouring column. `GestureTracker` counts pressed pointers (window capture phase, so it sees pointerups captured by OrbitControls): a multi-touch gesture is never a tap. Resizing the grid derives every new size from the village as it was before the first resize (`resizeSource` in `App.tsx`), so shrinking then growing back restores cropped blocks until the next edit. `App.tsx` memoizes `cells` on the render tick so pointer-move re-renders never trigger a merge rebuild.
- **Loading screen**: `#app-loader` is inline HTML + CSS in [index.html](../index.html), so it shows before any JavaScript is downloaded; a dusk scene: stars, moon, hills and the silhouette of a fortified town whose windows light up one by one, the title in spaced serif capitals, rotating progress messages and a thin indeterminate bar. The silhouette path and the window positions (percentages of a 960 × 240 frame) were generated by a script, not hand-edited. Every animation only touches `transform`/`opacity` on HTML elements (windows are `<i>` over the SVG, not SVG nodes), which the browser runs off the main thread, so it keeps moving while the first village build blocks it; under 520 px the title drops its side rules (they overflowed). `hideAppLoader()` ([src/loader.ts](../src/loader.ts), idempotent) fades it out: `VillageMeshes` calls it one `requestAnimationFrame` after the first frame rendered with its meshes mounted (geometries built, shaders compiled by that frame), and `main.tsx` calls it on any uncaught error or rejection, so a crash (no WebGL…) is never hidden behind it forever.
- **Toolbar & overlays**: [src/components/Toolbar.tsx](../src/components/Toolbar.tsx) (tools — build, demolish, raise / lower the ground —, history, generate/clear, ambience picker, share, screenshot, help), [src/components/HintCard.tsx](../src/components/HintCard.tsx) (first-run help, touch-aware). Their UI state (active tool, hint dismissed, screenshot capture callback, view mode — orbit or walk, see [walk.md](walk.md)) lives in [src/store/uiStore.ts](../src/store/uiStore.ts). Ambience presets are plain data in [src/config/ambiencePresets.ts](../src/config/ambiencePresets.ts), applied with `useControlStore.setState(preset.settings)`. The screenshot uses R3F `advance()` + `toDataURL()` in the same task (see `ScreenshotBridge` in `VoxelScene.tsx`) — don't enable `preserveDrawingBuffer` for it. UI colors are CSS tokens (`--ui-*`) in `styles.css`, which also themes Tweakpane through its `--tp-*` variables.
- **Control panel**: [src/components/TweakpanePanel.tsx](../src/components/TweakpanePanel.tsx) owns the Tweakpane `Pane` lifecycle and composes one `register*Controls(pane)` module per domain from `src/controls/` (grid, lighting, sky/fog, camera, post-FX, debug, actions) — each is a plain function returning a disposer, built with `registerStoreFolder(pane, { title, fields })` from [src/controls/storeFolder.ts](../src/controls/storeFolder.ts): a declarative list of `[storeKey, tweakpaneBindingParams]` written straight to the store (`[x, y, z]` tuples are edited as Tweakpane 3D points), and a folder only refreshes when one of its own keys changes. Add a setting by adding its key to the store (+ default, + migration if persisted users need it) and one line in the relevant module; add a new domain with one new module file + one line in `TweakpanePanel.tsx`'s `disposers` array. Village actions live in the toolbar, which reaches the imperative `VillageGrid` through [src/store/gridControllerStore.ts](../src/store/gridControllerStore.ts) (non-persisted) rather than prop-drilling.
- **External control (`window.villagecraft`, MCP server)**: [src/api/villagecraftApi.ts](../src/api/villagecraftApi.ts), installed by `main.tsx`, is the stable API for tools outside the app — describe / load / share the village, add or remove blocks like clicks, sculpt, generate, undo, settings and ambiences, camera, screenshot; every change goes through the grid controller (`commit()`), and the methods that change the scene resolve once the worker has rebuilt it and its blocks have finished appearing (`settled()`, reading `sceneBridge`). The scene registers what the API needs in [src/api/sceneBridge.ts](../src/api/sceneBridge.ts): camera get/set through OrbitControls (`makeDefault`, `CameraBridge` in `VoxelScene.tsx`), build in progress and last spawn time (`VillageMeshes.tsx`). Scripts must use this API rather than importing internal modules (the former capture script imported store modules and R3F's internal roots). [src/api/describeVillage.ts](../src/api/describeVillage.ts) (pure, tested) turns a grid into a height map, buildings, towers and arches for an agent; share codes live in the pure [src/store/villageCode.ts](../src/store/villageCode.ts) so Node tools can use them. The MCP server is in [tools/mcp/](../tools/mcp/README.md): a village edited in memory with the same rules as clicks, a share link, and screenshots rendered by a headless Chrome running the app (`VILLAGECRAFT_URL`); `npm run mcp`, registered for Claude Code in `.mcp.json`. `perf/` and `tools/` are type-checked through `tsconfig.tools.json`.
